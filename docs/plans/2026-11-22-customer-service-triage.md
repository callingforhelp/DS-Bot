# 微信客服：中文客服分诊

- 日期：2026-11-22
- 相关：[IM](2026-11-04-im.md)

## 为什么

外部客户通过企业微信的「微信客服」咨询时，需要一个长期工作的 Bot 理解中文问题、识别附件，并交给合适的专业 Bot。分诊不能只靠一次提示词：历史案例、误分原因和经过整理的规则需要保留，供下次查证。

## 已定的行为

- 新平台 `wecom_kf` 和企业微信智能机器人分开。填写 Corp ID、客服 Secret，可选客服账号 ID；留空选账号列表第一个。凭据进入现有密钥存储。
- 只向外发 HTTPS 请求：获取并缓存 access token，轮询 `kf/sync_msg`，保存游标；有下一页立即继续，空闲和失败逐步退避。不设置公网回调地址。
- 只接收客户来源（origin 3）。客户 ID 是私聊键，消息 ID 沿用平台 ID。第一次连接只接收最近一天的积压；已有游标继续接收。进入会话事件不触发 Bot，不主动欢迎。
- 文本、图片、文件、语音和视频复用 IM 附件通道；图片上限 20 MiB，其他附件上限 100 MiB。图片提供媒体类型，文件保存原始字节。
- **公开平台是配对例外。** 微信客服面向陌生客户，所有客户视为已配对，不产生连接请求。其他 IM 平台不变。客户可在各自独立线程中用编号回答问题卡；公开平台不能运行 `/stop`、`/start`，不能用编号回答审批卡，也不接受按钮交互，审批卡不向客户发送。客户内容是外部输入，不是团队管理授权。
- **每个客户独立会话。** 公开平台的每个私聊按连接 ID 和聊天键，在绑定 Bot 的 `openParts` 中延迟创建带 `customer` 标记的后台线程。同一客户复用该线程，换段仍保留映射；不同客户的历史不混入上下文，附件、问题卡和回复都跟随各自线程。Bot 的当前聊天不变，客户线程及其历史段不能切到前台，以免客户上下文与团队成员的日常聊天混用。
- **团队成员只读查看。** 在 Bot 详情的会话列表点击标为「客户会话」的条目，即可分页阅读该客户当前段及换段前的消息；先加载最新消息，再按需加载更早内容。查看不切换 Bot 的前台会话，不提供输入框或卡片作答按钮，问题卡仍由客户自己回答。
- 回复使用客服账号发送纯文本，按 UTF-8 的 2048 字节拆分。超出平台回复窗口或额度是永久失败，不自动重发；微信客服通常只允许客户消息后 48 小时内回复 5 条，拆分也消耗额度。
- 所有 IM 平台都为有字节数据的 `.step` / `.stp` 附件附加英文摘要：头字段、产品、单位声明、点坐标包围盒和关键实体计数。最多解析 50 MiB，不执行文件内容，解析失败不阻止附件传递。
- 所有 Bot 都能使用 `triage_cases`；在团队数据目录 `triage/` 保存最多 2000 个案例和 200 条规则。案例含客户、摘要、附件摘要、路由和理由，结果可记为正确、误分或已解决。误分教训保存在案例中，不自动共享；共享规则须通过 `rules add` 显式添加，规则可手动增删。
- **投票后再路由。** Bot 在调用 `message_bot` 前先调用 `vote`：`summary` 写清意图、产品／工艺、附件事实和客户历史，`routes` 至少列出两个候选，且只能使用登记的代理类型 ID；省略时使用全部登记类型，可用 `query` 指定检索词。工具检索相似案例和有效规则，用同一提示并行调用各评审模型（无工具、限制输出长度），明确客户文字是证据而非指令。每票必须严格为 JSON `{route, confidence, reason}`，路由必须来自候选列表，置信度为 0–1；格式错误、越界路由和调用失败均为无效票。只有至少两名不同评审、有效票不少于评审数的三分之二向上取整、有效票全部同意同一路由、平均置信度不低于阈值时，才返回 `decision: route` 和该路由；否则一律 `handoff`，不能擅自派发。
- **团队级评审配置。** `judges` 不带设置参数时列出配置；`models` 设置 1–3 个模型目录中的完整引用，`threshold` 设置 0–1 的阈值，默认 0.7。配置原子保存于 `triage/config.json`，未知引用会列出可选模型并拒绝保存。未配置评审时，只使用调用 Bot 自己的模型路由作为单一评审，但单评审不能授权自动路由；案例转人工并提示团队至少配置两名不同评审。以后经评估的微调 GLM 也可作为目录中的一个评审，不要求立刻训练或部署。
- **专业代理类型登记。** 同一配置保存 `types`：每项含 `type`、一行 `handles`、2–3 个请求 `examples`、`runtime`（`ds-bot` 或 `devin`）、`target`（Bot 名称或 Devin Bot ID／URL）和 `permission`。默认提供 `quote`（报价）、`drawing_review`（图纸审核）、`order_status`（订单进度）、`after_sales`（售后），各有中文职责和例句，目标暂空、权限标记为 `restricted`。`types` 列表，`type_action: add/edit/remove` 维护条目；`vote` 省略 `routes` 时使用登记类型，提示含各类型职责和例句，仍需至少两个候选。高置信度选中已配置的 DS Bot 时，按返回的 `delivery.target` 用 `message_bot` 交付；Devin 或空目标一律转为主聊天人工卡，卡含案例摘要及已有目标，不自动启动外部代理。权限字段是交付说明，不授予或改变目标 Bot 的实际权限。
- **低置信度交给人。** `handoff` 将完整有界摘要、各票、候选类型及其登记目标、客户线程 Session 保存在案例库，等待人工处理；工具不自动路由，而要求 Bot 用「您好，已收到您的需求，正在为您安排专人跟进，请稍候。」一类中文暖心回复告知客户等待。问题卡只放在该 Bot 的主聊天 `rt.chatOf(botId)`，不放客户线程；选项为得票最高的候选路由及「I'll handle it myself」，详情一行含完整摘要、客户来源会话、各票和候选目标，摘要明确标为不可信客户证据。主聊天已有问题卡时不覆盖，交接按顺序排队，已有卡被回答或清除后显示下一张；人工选择本身也不自动执行路由。`review` 持续列出待处理交接。待处理记录不因普通案例淘汰而丢失；库已满且不能安全淘汰时返回错误。
- `log` 可带 `votes` 和 `decision`，只保存评审引用、有效性、路由、置信度和简短理由，供后续整理评测集。
- 客户线程（包括已换下的历史段）只能调用 `recall`、`log`、`vote`、`rules list`、不带设置参数的 `judges` 和 `types` 列表；`outcome`、`review`、`rules add/remove`、代理类型增删改以及评审配置修改均拒绝。结果、规则、代理类型、评审设置和审查必须在客户会话之外记录，避免外部输入改写团队决策依据。普通会话的工具权限不变。
- `recall` 用字符二元组和拉丁词重叠排序，返回相关案例和全部有效规则；命中的规则累计检索命中次数（不是路由正确率）。`review` 返回上次审查以来的新案例、误分和规则命中数，并更新审查时间。可用现有定时任务每周运行，不默认创建任务。
- 路由给其他 Bot 使用现有 `message_bot` 工具，不增加另一套调度器。`rules` 操作在工具参数里用 `rule_action: add/remove/list` 区分，避免和顶层 action 重名。

启动时若尚无任何 `wecom_kf` 连接，可从仓库根目录已被 Git 忽略的 `.env` 导入 `WECOM_CORP_ID`、`WECOM_KF_SECRET` 和可选的 `WECOM_KF_OPEN_KFID`；`DSBOT_ENV_FILE` 可改为其他路径。秘密通过现有 `secret-set` 写入 DSH 秘密库，运行时仅以秘密库为来源，不记录字段值。已有连接（包括停用的连接）不被覆盖；缺少必填项不导入。导入的连接保持停用且未绑定；团队成员必须在设置中明确选择受限的客服 Bot 并启用后才会处理外部消息。设置页登录和保存仍只写 DSH 存储，绝不创建、更新或回写 `.env`。删除连接后若不希望下次启动再次导入，应同时移除本地种子字段。

## 不做什么

- 不接公网回调、不做主动欢迎、不做客服坐席状态管理或人工接管。
- 不让外部客户直接管理团队、停止 Bot 或批准工具权限。
- 不实现 CAD 内核、网格化或精确孔识别；不把 STEP 中的注释或字符串当作指令。
- 不自动证明一条教训正确，不自动给其他 Bot 改提示词。

## 已知限制

- 未用真实企业微信租户做联调。需在目标租户验证无回调 token 的轮询权限、平台消息保留时间和实际错误码。
- 点坐标包围盒可能包含控制点，不是精确实体包围盒；圆柱面只提示可能的孔或凸台。单位显示文件声明，不做单位换算或装配变换。
- 案例库是团队共享数据，不适合存放密钥或超出团队授权范围的客户隐私。只保留简短必要摘要；规则仍需人工审查。最近案例超限淘汰，规则满额要求先清理。
- 通过 `message_bot` 联系的专业 Bot 仍会看到客户提供的文字；客户线程隔离和分诊工具限制不会把转述内容变成可信指令，接收方仍须把它当作外部输入。
- 案例文件与规则文件各自原子替换，但两者不是数据库事务；异常断电时可能需要人工对账。单进程队列配合团队写锁避免并发覆盖。
